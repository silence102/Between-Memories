# TIL: Claude-Oriented 아키텍처를 쉽게 이해하고 잘 쓰는 방법

작성일: 2026-02-11
대상 레포: `Between Memories`
연관 문서: `docs/ARCHITECTURE.md`, `README.md`

## 이 문서의 목적
이 문서는 "현재 아키텍처가 이전 방식보다 왜 나은지"와 "실제로 어떻게 써야 효과가 나는지"를 빠르게 이해하기 위한 학습 자료다.

## 1) 이전 버전 대비 무엇이 좋아졌나
아래 비교에서 "이전 버전"은 보통 초기에 많이 쓰는 단순 구조(단일 모델 호출 + 약한 가드레일)를 의미한다.

| 관점 | 이전(단순 구조) | 현재(Claude-Oriented 구조) | 실제 효과 |
|---|---|---|---|
| 모델 사용 | 요청마다 같은 모델 고정 | 작업 난이도별 라우팅(Haiku/Sonnet/Opus) | 품질 유지 + 비용 최적화 |
| 비용 통제 | 사후 확인(월말 정산 느낌) | 요청 전 토큰 예산 검증 + 라우팅 정책 | 과금 사고 예방, 예측 가능성 증가 |
| 안정성 | 재시도/타임아웃이 흩어짐 | 게이트웨이에서 공통 처리 | 장애 대응 일관성 향상 |
| 개발 속도 | 팀원마다 호출 방식 다름 | 단일 진입점(`ClaudeGateway`) | 유지보수/온보딩 속도 향상 |
| 운영 관찰성 | 로그가 파편화됨 | usage/latency/error를 구조적으로 수집 가능 | 병목/비용 원인 분석 쉬움 |
| 안전성 | 실수 명령 방어 약함 | `.claude/settings.json` + pre-hook | 위험 명령/민감 정보 접근 위험 감소 |

핵심 요약:
- 이전 구조는 "빨리 시작"은 쉽지만, 트래픽/팀 규모가 커질수록 품질 편차와 비용 리스크가 급증한다.
- 현재 구조는 "처음부터 운영 가능한 기본선"을 깔아서, 기능 개발과 운영 안정성을 동시에 가져간다.

## 2) 지금 이 아키텍처가 좋은 평가를 받는 이유
## 2-1. 기술적으로 설득력이 높다
1. 모델 라우팅이 명시적이다.
- `quick/build/critical` 같은 정책 키로 의사결정을 코드에 남긴다.
- "왜 이 모델을 썼는지"가 설명 가능해진다.

2. 비용 제어를 코드 레벨에서 강제한다.
- `MAX_INPUT_TOKENS`, `MAX_OUTPUT_TOKENS` 같은 상한선이 있어 사고를 줄인다.
- "일단 호출하고 나중에 보자" 패턴을 막는다.

3. 운영 기능(재시도/가드/관측)을 아키텍처 중심에 둔다.
- 기능 코드와 운영 코드가 분리되어 장애 대응이 쉬워진다.

## 2-2. 실제 사용자 그룹별로 체감 이점이 분명하다
1. 1인 개발자/소규모 팀
- API 호출 표준화로 시행착오가 줄고, 첫 서비스 출시 속도가 빨라진다.

2. 스타트업 제품 팀
- Sonnet 중심 개발 + 필요 시 Opus 에스컬레이션으로 품질/비용 균형을 맞추기 쉽다.

3. 운영/플랫폼 담당자
- 비용/지연/오류를 같은 축에서 추적할 수 있어 정책 개선이 빠르다.

4. 보안/품질 담당자
- 민감 파일 접근 제한과 위험 명령 차단 같은 기본 안전장치가 갖춰져 감사 대응이 수월하다.

## 3) 아키텍처를 쓰는 사람의 이해 프레임
이 구조는 "모델을 잘 고르는 기술"이 아니라 "업무를 계층으로 분리하는 습관"으로 이해하면 쉽다.

1. API 계층: 계약을 명확히 한다.
- 입력/출력 스키마를 먼저 확정한다.
- 예: `AiRequest`, `AiResponse`

2. 오케스트레이션 계층: 요청을 해석한다.
- 이 요청이 `quick/build/critical` 중 무엇인지 판단한다.

3. 게이트웨이 계층: 모델 호출은 한 곳에서만 한다.
- 재시도/타임아웃/usage 수집을 공통 처리한다.

4. 가드레일 계층: 사고를 "사전에" 막는다.
- 토큰 초과, 위험 명령, 민감 경로 접근을 선제 차단한다.

5. 관측 계층: 개선 루프를 만든다.
- 어느 엔드포인트가 비용을 많이 쓰는지, 어떤 모델이 병목인지 추적한다.

## 4) 이 레포에서 실전으로 쓰는 순서
1. `task_type`을 먼저 정한다.
- 빠른 처리: `quick`
- 일반 기능 작업: `build`
- 정확도 최우선: `critical`

2. 프롬프트를 바로 길게 쓰지 않는다.
- 먼저 요약/분류 단계를 거쳐 입력 토큰을 줄인다.

3. 실패를 정상 흐름으로 설계한다.
- 예산 초과 시 400 응답 후 요약 요청으로 재시도하도록 클라이언트 전략을 둔다.

4. 운영 지표를 함께 본다.
- 기능 완료 기준에 "응답 품질"뿐 아니라 "토큰/지연"을 포함한다.

## 5) 자주 발생하는 오해와 안티패턴
1. "좋은 모델 하나로 통일하면 더 낫다"
- 단기적으로 단순해 보이지만, 비용과 대기시간이 빠르게 악화된다.

2. "예산 제한은 나중에 붙여도 된다"
- 실제로는 사고 이후에 붙이면 코드/운영 모두 비용이 더 커진다.

3. "프롬프트 품질만 좋으면 된다"
- 운영에서는 재시도, 관측, 실패 전략이 없으면 품질이 유지되지 않는다.

## 6) 학습용으로 보면 좋은 체크리스트
매 기능 개발 시 아래 6개를 점검한다.
1. 이 요청의 `task_type` 근거가 명확한가?
2. 입력 토큰을 줄일 전처리(요약/분할)가 있는가?
3. 실패 시 폴백/재시도 정책이 정의됐는가?
4. 토큰/지연/오류를 기록하고 있는가?
5. 민감 정보가 로그/프롬프트에 직접 노출되지 않는가?
6. 테스트가 계약(스키마, 상태코드, 오류 케이스)을 검증하는가?

## 7) 이 구조로 배우면 얻는 역량
- 모델 선택을 감으로 하지 않고, 정책으로 설계하는 능력
- 품질/속도/비용을 동시에 다루는 운영 감각
- AI 기능을 "한 번 동작"이 아니라 "지속 운영" 관점에서 구현하는 습관

## 마무리 한 줄
이 아키텍처의 강점은 "최고 성능 모델을 쓰는 것"이 아니라, "필요한 품질을 가장 낮은 비용으로 안정적으로 반복 생산"하는 데 있다.
